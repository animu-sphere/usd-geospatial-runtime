# A hosted SDK lane exposes producer Python paths in the OpenUSD runtime

- Date: 2026-09-18
- `ost`: 0.22.10 (`x86_64-pc-windows-msvc`, SHA-256 verified)
- Target: `windows-x86_64-msvc143-py313`
- Occasion: PR [#7](https://github.com/animu-sphere/usd-geospatial-runtime/pull/7), the first hosted Windows OpenUSD SDK lane
- CI run: [35239920262](https://github.com/animu-sphere/usd-geospatial-runtime/actions/runs/35239920262)
- OpenUSD artifact: `sha256:51c19df2725955adfc3ef2e96ba6da6561d332a923275eb133c3802a1f659a1c`
- OpenUSD OCI manifest: `sha256:1c63272c417f43fbded784b6ab88cb5dac6bb58e87d9e69e254f10b87cff3143`
- Prior related report: [usd-vrm-plugins report 37](https://github.com/animu-sphere/usd-vrm-plugins/blob/main/docs/reports/ost/37-2026-08-30-v0.22.6-runtime-python-paths-from-the-producer.md)
- Status: OpenUSD CI lane disabled pending a relocatable runtime package

## TL;DR

The first hosted run did not reach a C++ compile or test. It composed the
locked runtime successfully, then failed while configuring the SDK at
`find_package(pxr)`:

```text
Could NOT find Python3 (missing: Development Development.Module Development.Embed)
Development: Cannot find the library
"C:\Users\snkm\AppData\Local\Programs\Python\Python313\libs\python313.lib"
Development: Cannot find the directory
"C:\Users\snkm\AppData\Local\Programs\Python\Python313\Include"
```

The runner had Python 3.13.15 under the hosted tool cache. The paths in the
error belong to the machine that produced the OpenUSD runtime artifact, not to
the runner.

This is a packaging defect in the published OpenUSD CMake package, not a
failure of `ost runtime compose`, the repository's core SDK lane, or the SDK
source. The OpenUSD job is disabled in CI until the runtime is republished
without producer-local paths or a complete, tested consumer-side repair exists.

## 1. What the lane ran

The job was intentionally a consumer-style path rather than an OpenUSD build:

1. Install Python 3.13 with `actions/setup-python`.
2. Download the pinned `ost 0.22.10` Windows CLI and verify its archive digest.
3. Run:

   ```powershell
   ost runtime compose targets/windows-x86_64-msvc143-py313/composition.toml `
     --lock targets/windows-x86_64-msvc143-py313/lock.json --locked `
     --output .local/composed
   ```

4. Configure `sdk/` with the materialized prefix as `pxr_ROOT` and
   `CMAKE_PREFIX_PATH`.
5. Build and test the OpenUSD SDK, install it, and build the external consumer.

The other repository checks were not affected: `metadata` and `sdk-core`
passed. `sdk-usd` failed at step 4, before its build and tests.

## 2. The mechanism

The materialized prefix's `pxrConfig.cmake` contains the following pattern:

```cmake
if (NOT DEFINED Python3_EXECUTABLE)
    set(Python3_EXECUTABLE [[C:/Users/snkm/AppData/Local/Programs/Python/Python313/python.EXE]])
endif()
if (NOT DEFINED Python3_LIBRARY)
    set(Python3_LIBRARY [[C:\Users\snkm\AppData\Local\Programs\Python\Python313\libs\python313.lib]])
endif()
if (NOT DEFINED Python3_INCLUDE_DIR)
    set(Python3_INCLUDE_DIR [[C:\Users\snkm\AppData\Local\Programs\Python\Python313\Include]])
endif()
find_dependency(Python3 "3.13" EXACT COMPONENTS Development)
```

The guards make these three values overridable, but the current workflow only
passes `pxr_ROOT` and `CMAKE_PREFIX_PATH`. `Python3_ROOT_DIR` would not be the
matching override: the package has already set the three variables before
`FindPython3` runs.

There is a second, stronger relocation problem in the same package. The
materialized `cmake/pxrTargets.cmake` contains the producer's Python include
directory in 16 imported-target entries. Those literal
`INTERFACE_INCLUDE_DIRECTORIES` values are not repaired by passing CMake
variables.

## 3. What was measured

### 3.1 The failure reproduces only when the producer path is foreign

On this workstation, the producer path exists. The same unmodified package
therefore configured, built, and tested successfully locally. That green result
was not evidence that the artifact was consumable from another host.

A fresh local configure with explicit `Python3_EXECUTABLE`,
`Python3_LIBRARY`, and `Python3_INCLUDE_DIR` values also configured
successfully. This confirms that the first `pxrConfig.cmake` layer accepts the
override, but this workstation uses the producer path itself and therefore
does not simulate the foreign runner. It also does not close the 16 imported
target include entries described above, so it is not yet a complete repair.

### 3.2 The alternate `26.08-gl-windows-x86_64` package is not a clean fix

The package at
[openstrata-runtime-cy2026-usd/1167189198](https://github.com/orgs/animu-sphere/packages/container/openstrata-runtime-cy2026-usd/1167189198?tag=26.08-gl-windows-x86_64)
contains a different archive:

- OCI manifest: `sha256:d3ff79a6f330558c3b9a427a927d340fe3dcab1fe89107faa0ea9f66a104b7bf`
- OpenStrata artifact: `sha256:ebb0c7da509ee14ada19ee5b461de6996aad0024b5c9640f12dde76912e849b5`
- Target in the artifact manifest: `windows-x86_64-msvc143-py313`
- Python compatibility: CPython `3.13.x`, producer `3.13.14`
- Runtime identity: `sha256:3a4e399351763a5ef55575e5341b28adabf1ffe6cf55a1d3cc315e19aba9dbff`

It is therefore the same OpenUSD runtime identity by a different archive, and
it is a technically compatible replacement candidate after a fresh
composition. Its extracted `pxrConfig.cmake` nevertheless contains the same
producer-local Python paths. Swapping it into this release would also require
a new composition lock, generated metadata, and release evidence; it would not
resolve the hosted configure failure by itself.

## 4. What this repository did

- Kept the current lock and released OpenUSD artifact unchanged.
- Disabled only the `sdk-usd` job in [`.github/workflows/ci.yml`](../../../.github/workflows/ci.yml) so the metadata and OpenUSD-free core lanes remain active.
- Recorded the failure here rather than treating the local green run as
  evidence of portability.
- Left the explicit `Python3_*` override as a measured workaround candidate,
  not as a fix, because the imported-target layer still needs a complete repair.

## 5. The ask

**P1 - publish a relocatable OpenUSD CMake package.** A runtime artifact is
pulled by consumers that did not build it. Its exported CMake package must not
require the producer's filesystem layout.

At minimum:

1. `pxrConfig.cmake` should let `FindPython3` resolve the consuming host's
   Python development files rather than defaulting to producer-local paths.
2. `pxrTargets.cmake` should not write a producer-local Python include path into
   imported targets. It needs a consumer-resolvable form, or the package must
   provide a documented relocation step that is applied before configuration.
3. A clean-host CMake consumer check should exercise both layers. Configuring
   only the package config is insufficient when imported targets are later
   validated by CMake.

**P2 - make the failure visible in runtime validation.** A runtime validation
that reports a package as consumable should either exercise an external CMake
consumer against the installed prefix or state clearly that it has not tested
that boundary.

## 6. Current status

The `sdk-usd` job remains disabled. Re-enable it only after either:

- a republished OpenUSD runtime passes the clean Windows consumer configure,
  build, and test path; or
- this repository carries a complete repair for both exported-CMake path layers
  with focused validation and an explicit record of the repaired external
  prefix.
